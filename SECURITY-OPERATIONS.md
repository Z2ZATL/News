# Z2Zs Lab security operations

## Deployment boundary

- `news.z2zs.space`: public Next.js application
- `studio.z2zs.space`: separate Sanity Studio origin, Sanity-authenticated and noindexed
- `z2zs.space`: existing corporate and mail domain; do not redirect or change mail records

## DNS change rule

Inspect the live Cloudflare zone before every change. The production site is on
Netlify; change only an explicitly approved application CNAME. Never delete or
replace existing `brief`, `preview.brief`, MX, DKIM, or tracking records.

The apex DMARC rollout is currently `p=quarantine; pct=25; sp=none`. Do not
advance it further until aggregate reports prove that every legitimate sender
passes aligned SPF or DKIM.

The application hostnames are CNAMEs and therefore cannot carry null MX or SPF
TXT records at the same owner names. After exact DNS approval, publish explicit
`p=reject` policies at `_dmarc.news.z2zs.space` and
`_dmarc.studio.z2zs.space`; keep the apex in monitoring during the sender audit.
ADR 0005 records the standards constraint and the approved record shape.

## Required secrets

- `SANITY_API_READ_TOKEN`: viewer only, public site server
- `PREVIEW_TICKET_SECRET`: random 32 bytes, server functions only in the public
  and Studio projects. It must never use a `SANITY_STUDIO_` prefix.
- `SANITY_WEBHOOK_SECRET`: generated by Sanity webhook configuration
- `UPSTASH_REDIS_REST_URL` and `UPSTASH_REDIS_REST_TOKEN`: server-only replay,
  reaction, and application rate-limit storage

Never prefix a secret with `NEXT_PUBLIC_`.

## Draft preview protocol

Sanity Studio links to a server-side preview broker on the protected Studio
origin. Studio sends its current Sanity user-session token to that same-origin
broker in an `Authorization` header. The broker forwards it only to the fixed
project-specific Sanity `/users/me` endpoint and requires an editor, developer,
or administrator role. It never logs, persists, redirects, or returns the
session token. Only then does it create a signed, 60-second ticket containing
the document type, slug, locale, expiry, and a random identifier. The public
draft route verifies the ticket and atomically consumes its identifier before
enabling draft mode.

Never embed the ticket signing secret in the Studio bundle, send a reusable
secret or Sanity session token in a URL, or log preview authorization headers
or ticket query strings.

Application-level Redis limits protect draft-ticket attempts (5/minute), CSP
reports (10/minute), and reaction reads/writes even when a platform firewall
rule is unavailable. Do not remove these limits after adding host-level traffic
controls.

## Launch controls

- Netlify Deploy Preview tested before domain cutover
- Netlify Free hard credit limit; no auto recharge or paid add-ons
- Netlify sites are not connected to the private organization repository;
  deploy a reviewed commit manually through the authenticated CLI
- Application limits: `/api/draft` 5/min/IP, `/api/csp-report` 10/min/IP,
  reaction writes 20/min/IP and reads 60/min/IP
- Sanity CORS: production public and Studio origins only
- Studio requires Sanity authentication plus `X-Robots-Tag: noindex, nofollow`
- DNSSEC at Cloudflare and DS record at the registrar
- explicit application-subdomain DMARC records after approved DNS cutover
- registrar lock, hardware-key 2FA, independent recovery email

## Decommissioning

Delete a DNS record before deleting the corresponding hosted project. The
Vercel rollback window is closed; do not recreate a Vercel deployment or domain
claim without a new founder decision.

## Netlify release and rollback

1. Confirm the worktree is clean, the deployed commit is the reviewed PR head,
   and every required CI check passed.
2. Verify the Netlify preview with the same production environment variables.
3. Deploy only after the public quality job passes for the same commit.
4. Verify HTTPS, nonce CSP, headers, `/th`, both RSS feeds, sitemap, reactions,
   Sanity reads, and webhook invalidation from two independent networks.
5. If a critical check fails, publish the previous reviewed Netlify release and
   verify the same surfaces again.

The scheduled `production-audit.yml` workflow is fail-closed for the public
news site: it checks live headers, feeds, security endpoints, DNSSEC, and the
exact public CNAME every month. If the approved host changes, update
`AUDIT_PUBLIC_CNAME` in the reviewed workflow; do not weaken it to a suffix
match or disable a readiness check.
